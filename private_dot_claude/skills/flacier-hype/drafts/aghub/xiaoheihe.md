# 你的 Steam 存档该归你，AI 编程工具的配置也一样

之前在盒里发过一个 Steam 存档的东西，聊过一个观点：存档是你打出来的，就该归你——你能自己翻出来看，能拷走，能删，不用求谁。云同步是帮你多存一份，不是把你那份收走。这条线我一直没变。

换到 AI 编程工具上，同一个问题又回来了，而且更别扭。

桌面上现在同时挂着 Claude Code、Codex、Cursor、Copilot、Gemini 一堆 AI，每个都有自己一份配置：MCP server、skill、模型、API key。装的越多，配置越散，改一次得在好几个地方各改一遍。管这摊事的工具是有的，但一个管配置的工具，对你已经写好的那些文件，其实只有两种态度：接管，或者服务。选哪种，基本决定了它是什么东西。

## 接管：CC Switch 走的这条路

我用 CC Switch 用了大半年。它选的是接管。

它把 provider 配置收进自己的一个数据库，以这份库为准。每次切换，它拿库里的版本，把 `settings.json`、`config.toml` 整份重写一遍。你目录下那份配置文件，在它眼里就是一个被覆盖的输出。

第一次启动它就把你现有配置导进库里，从那一刻起，真正生效的状态就不在你的文件里了。你在 shell 里设的环境变量作废，因为 `settings.json` 归它写，Claude Code 只认它写进去的值。你想知道它到底动了哪几个字段，没办法，配置在库里，不是一份你能打开、能 diff 的文本。你手写的、没进它库的那些 plugins、MCP、permissions，下次切换可能就没了。

这不是它哪一版没写好，是它的取向就这样：配置存它的库，对外整份覆盖。托管的意思就是，你得信它保管得住。存档收进别人的库、以库为准、你自己看不到改了什么——这不就是我当年吐槽 Steam 存档时不想要的那套。我不想信，我想自己拿着。

## 服务：aghub 走的这条路

后来我自己写了个工具，aghub，从头到尾只认一件事：配置是你的，我帮你配好，不替你保管。

所以它增量编辑，不接管。它直接读你现有的配置文件，只改你显式指定的那几项，其余原样不动。不写全局状态，不注册后台 handler，不驻留进程。每次变更你都能 diff 出来看，改了什么一目了然。哪天不想要某条了，把对应条目删掉就行，零残留——它没往别处偷偷存过东西，也就没东西可残留。

配一次 MCP，能推到全部 22+ 个 agent；也能一条命令审计所有 agent 现在装了哪些 server；不想删又想临时关掉，可以禁用。key 存在系统原生 keychain 里，不落明文配置。这些都建立在同一个前提上：你的文件始终是你的，我只在你让我动的地方动。

## 连代码里都是这个原则

多说一句实现，因为这条原则不是嘴上说说，是写进代码结构里的。

aghub 里每个 agent 就是一张静态的 `AgentDescriptor`——解析、序列化、路径、能力声明，都以函数指针挂在这张描述符上。加一个新 agent，就是加一个文件、把它注册进 `ALL_AGENTS`，不往主流程里塞特例。所以它能同时扛住 22+ 个格式各异的 agent，还能保证「只改你指定的那几项」这件事在每一家身上都成立。

各家格式的差异也是老老实实按各家来的，不硬抹平。Claude 的 skill 不进 JSON，是去扫 `~/.claude/skills` 里的 `SKILL.md`；OpenCode 用 `mcp` 对象 key 而不是 `mcp_servers` 数组；Codex 用 TOML，只吃 stdio、不支持远程 MCP。这些差异 aghub 都照着实现，而不是套一个统一模板然后写坏别人的文件。

## 边界

CC Switch 那几条是我翻它行为、自己用大半年下来的判断，哪一条它最近改了、和我说的不一致，欢迎指出来。aghub 是 Rust 写的、开源、跨平台，Windows 目前标 experimental。

代码在这：github.com/akarachen/aghub，官网 aghub.akr.moe。想自己拿着自己的配置，就来试试。
